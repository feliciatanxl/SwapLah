## Details of Usage

I declare that I have used Artificial Intelligence (AI) tools to assist in the development of this assignment in the following ways:

1. **Database Schema Design:** Used AI assistance to design the `offers` table, including fields for `listing_id`, `buyer_id`, `offer_type`, `proposed_price`, `swap_listing_id`, `status`, and `created_at`. The schema was reviewed to ensure referential integrity via foreign keys to the `listings` and `users` tables.

2. **Backend API Development:** Used AI assistance to plan and implement the `POST /api/offers` route in `app/routes/offers.py`. This included structuring the handler into focused helper functions (`_validate_common`, `_handle_cash_offer`, `_handle_swap_offer`) to reduce cyclomatic complexity and keep each function single-purpose.

3. **Input Validation Logic:** Used AI assistance to implement validation for both offer types:
   - Cash offers: requiring a non-negative numeric `proposedPrice`.
   - Swap offers: verifying the `swapListingId` exists in the buyer's own active listings.
   - Both: preventing a buyer from submitting an offer on their own listing, and requiring authentication.

4. **Database Helper Functions:** Used AI assistance to implement `get_listing_owner()`, `get_active_listing_by_buyer()`, and `create_offer()` in `app/db.py`. Each function was reviewed and tested to confirm correct SQL behaviour.

5. **Unit Test Creation:** Used AI assistance to write `tests/unit/test_offers_unit.py`. Tests cover all acceptance criteria using monkeypatching to isolate the route layer from the database. Both positive (happy path) and negative (validation failures, ownership checks) scenarios are included.

6. **API Integration Test Creation:** Used AI assistance to write `tests/api/test_offers_api.py`. Tests use a real temporary SQLite database with seeded users and listings, covering all AC for both cash and swap offer flows.

7. **Code Quality Improvements:** Used AI assistance to restructure `offers.py` and `listing.py` to address pylint feedback — correcting import ordering, adding module and function docstrings, reducing boolean expressions in conditionals, and splitting large functions for readability.

8. **Debugging:** Used AI assistance to troubleshoot blueprint registration, session handling in tests, and SQLite foreign key behaviour during development.

## Sprint 3 Update — Offers and Transactions (Manage Received Offers)

### Additional AI Tools Used

- **Tool Name:** Claude (Anthropic)
- **Purpose:** Backend API design for managing received offers, database schema extension, merge conflict resolution guidance, and test generation for Sprint 3 user stories.

### Details of Usage

1. **View Pending Offers:** Used AI assistance to design and implement `get_offers_for_seller()` in `app/db.py`, which joins `offers`, `listings`, and `users` to return all offers received on a seller's listings, and the `GET /api/offers/received` route in `app/routes/offers.py`.

2. **Accept Offer:** Used AI assistance to implement `accept_offer()`, which marks an offer as `Accepted`, marks the listing as `Sold`, and records a transaction, along with the `PATCH /api/offers/<id>/accept` route with ownership and status validation.

3. **Reject Offer:** Used AI assistance to implement `reject_offer()` and the `PATCH /api/offers/<id>/reject` route, ensuring only the listing owner can reject a pending offer and that other offers on the listing are left untouched.

4. **Auto-Reject on Accept:** Used AI assistance to extend `accept_offer()` so that accepting one offer automatically marks all other pending offers on the same listing as `Rejected`, satisfying the "only one successful transaction per listing" requirement.

5. **Transaction Table and History:** Used AI assistance to design the `transactions` table, the `get_transactions_for_user()` query (separate SQL for buyer vs seller views), and the `GET /api/transactions` route used to power the Transaction History page.

6. **Shared Validation Helper:** Used AI assistance to extract `_check_offer_access()` as a shared helper for the accept and reject routes, reducing duplicated authentication, ownership, and status-check logic.

7. **Test Creation:** Used AI assistance to write unit tests (`tests/unit/test_manage_offers_unit.py`, `tests/unit/test_transaction_history_unit.py`) using monkeypatching, and real-database integration tests (`tests/api/test_accept_reject_offers_integration.py`, `tests/api/test_transaction_history_api.py`) that seed actual SQLite data to verify the auto-reject SQL and transaction history queries end to end, rather than relying on mocks alone.

8. **Merge Conflict and Git Workflow Debugging:** Used AI assistance to resolve several merge conflicts between my feature branch and `develop` (in `app/db.py`, `app/routes/offers.py`, and `app/templates/listing_detail.html`), recover from an accidental merge on the wrong branch, and diagnose a `sqlite3.OperationalError: database is locked` issue by adding a busy timeout and WAL journal mode to `get_db_connection()`.

### Refinement of AI Output

- All new database functions were manually traced through to confirm correct SQL joins and update ordering (e.g. accepting an offer updates the offer, rejects competing offers, and updates the listing status in a single connection before committing).
- Ownership and status-check logic was tested against edge cases: non-owner access, already-resolved offers, and missing offers.
- The auto-reject behaviour was specifically verified using a real temporary SQLite database (not just mocks) to confirm the `UPDATE ... WHERE status = 'Pending'` clause behaves correctly with multiple competing offers.
- Test cases were extended beyond the initial AI draft to cover empty states (no offers, no transactions) and data isolation (a user cannot see another user's transactions).
