## Details of Usage

I declare that I have used Artificial Intelligence (AI) tools to assist in the development of this assignment in the following ways:

1. **Reviews Database Schema:** Used AI assistance to design the `reviews` table in `app/db.py`, including `offer_id`, `reviewer_id`, `reviewee_id`, `rating`, and `comment` columns with foreign keys to `offers` and `users`. AI also helped write `ensure_reviews_schema()`, a migration helper that safely drops and recreates an outdated `reviews` table left over from an earlier branch (matching the existing `ensure_listing_status_column()` pattern), so teammates pulling the branch would not hit a schema mismatch.

2. **Average Rating Calculation:** Used AI assistance to implement `get_user_rating_stats()`, which computes a user's average rating and review count on read (via `AVG(rating)`/`COUNT(*)` over the `reviews` table) rather than storing a cached value, so the figure shown is always derived from current data. I reviewed the rounding behaviour and the `None` result for users with zero reviews.

3. **Profile Rating Display (View Another User's Rating):** Used AI assistance to add the `/profile/<user_id>` route (`view_profile`) so a user can view another user's profile, average rating, and review list, while redirecting to `/profile` if the user views their own ID. AI helped implement the "No reviews yet" empty state in `profile.html` and add a public profile link from the listing detail seller card.

4. **Review Retrieval Endpoint:** Used AI assistance to implement `GET /api/users/<user_id>/reviews` in `app/routes/reviews.py`, returning the review list, average rating, and review count as JSON, with a 404 for a non-existent `user_id`.

5. **Buyer Review Submission (#36, #44):** Used AI assistance to implement and harden `POST /api/reviews` so a buyer can leave a 1–5 star rating and optional comment for a seller after a completed transaction. AI helped add validation to reject ratings outside 1–5 (including non-integer and boolean values), reject reviews on a non-`Accepted` offer, and reject a review submitted by anyone other than the offer's buyer, deriving the reviewee from the transaction instead of trusting a client-supplied ID.

6. **Seller Review Submission (Bidirectional Reviews):** Used AI assistance to extend the same endpoint so a seller can also review the buyer of a completed transaction, symmetric to the buyer→seller flow. AI helped generalise the participant/reviewee checks so either party of an `Accepted` offer can review the other, while a third party not involved in the transaction is rejected with a 403.

7. **Merge Conflict Resolution:** Used AI assistance to resolve merge conflicts in `app/db.py` and `app/__init__.py` after pulling the latest `develop` branch, which had refactored the database layer (SQL moved into module-level constants) and split `create_app()` into `_register_*` helper functions. AI helped reconcile develop's refactor with the reviews feature work, restoring the `reviews` table creation in `init_db()`, the `view_profile` route, and the `rating`/`reviews`/`seller_rating` template context that had been dropped by the conflicting structure, and adding `view_profile` to the public-endpoint allowlist used by develop's session-timeout check.

8. **Verification:** Used AI assistance to verify all of the above end-to-end using the Flask test client — covering each acceptance criterion for the review stories (valid/invalid ratings, incomplete transactions, uninvolved users, empty-state and populated profiles) and confirming the full pytest suite (134 tests, excluding Selenium) still passed after the merge. I reviewed the test output myself before treating the work as complete.
